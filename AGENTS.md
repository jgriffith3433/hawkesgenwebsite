> `cloud/functions/.env.<project>` and `test/lanes.test.ts` in `cloud/functions` checks them (docs/cloud.md "Lanes"). Checks: `cd cloud/functions && npm ci && npx tsc -p .` (plus the old `npm test` for
> `public/`). The sections below describe the old server; where they disagree with `docs/cloud.md`, docs/cloud.md wins.

The site paying customers use: the landing page and portfolio (`/`), the Creator Studio (`/app`), accounts, credits
and Stripe. It does no generation itself. **Hawkes Gen is the backend** (jobs, the GPU fleet, the library), and the
portal is one of its customers, exactly like Hawkes Studio: one Gen key, scoped in Gen to the projects `usr_*`.
Every customer is a project (`usr_<16 hex>`), and every call the portal makes for a customer carries
`X-Hawkesgen-Project: usr_...`, which narrows the key to that project inside Gen (`hawkesgen/src/auth.ts`). So Gen
itself keeps customers apart: jobs by id, events, assets, files, inputs and `slot:` references.

```
customer ──https──▶ hawkesgen.ai (this repo, its own EC2 box, Caddy, .data/portal.db)
                        │  Gen key (usr_*) + X-Hawkesgen-Project
                        ▼
                    Hawkes Gen (gen.hawkesgen.ai today; moves to Studio's new domain later) ──▶ GPU fleet, APIs
```

## Hard rules

- **Never give a customer a way to start Gen work without paying.** Only the routes listed in `src/server.ts`
  (`PASS_GET`, `PASS_POST`, `UPLOADS`) reach Gen as they are; `POST /v1/jobs` and `/v1/run` go through `src/jobs.ts`
  (quote, take credits, submit, settle). Never pass through rerun, entity make/revise, or anything else that queues a job.
  **The one exception is the free demo API** (`src/demo.ts`, `/v1/demo`; the landing's demo section was removed 2026-10-26, the API stays): only `image.transform` pixel art and
  `image.cutout` (Gen's CPU, no GPU), images up to 6 MB, `DEMO_PER_IP` (3) a day per address and `DEMO_PER_DAY` (300) for
  everyone, as the demo project `usr_0000000000000000`. Never add a GPU tool to it.
  (Levels of detail are not an exception: Gen makes them itself as part of making every image and model, its own
  `asset.lod` work, charged to nobody; the portal only reads them: `src/lods.ts`.)
- **MCP tools pay like everything else.** Every tool in `src/mcp.ts` either answers directly (account, lists) or starts a task (`src/tasks.ts`), whose steps go through `jobs.ts submit` with the caller's `via` (the daily limit). `/mcp` takes bearer tokens only (OAuth `hgo_` or an `hg_` key), never the session cookie: it has open CORS.
- **Credits are money.** Every change of a balance is a row in `credit_ledger` in the same transaction (`billing.ts add`).
  A job is charged once (`jobs` table) and given back once (unique `job_id, kind`); a Stripe session pays once (unique
  `stripe_session_id`). Keep those indexes and the tests in `test/portal.test.ts`.
- Prices come from Gen (`POST /v1/billing/quote`). Packs are in `billing.ts PACKS`.
- Secrets live in `.env` on the box (gitignored): `HAWKESGEN_KEY`, `STRIPE_SECRET_KEY`, `STRIPE_PUBLISHABLE_KEY`,
  `STRIPE_WEBHOOK_SECRET`. Never commit, print or log them.
- **Design:** the website is light (`body.landing` tokens in `public/public.css` + `public/site.css`, Inter headings, JetBrains Mono for code). The one exception is the landing page's hero (`public/overseer-sky.js` + `overseer-sky.css`): the Overseer's sky, dark like the game, which the page descends out of into the light (`/games` opens with the same sky, its featured games as planets, then the light "Made by players" section with the Live now / Most played / New tabs; both are meant); its wish box is a preview of the beam, not a build, and says so. Otherwise only the game is dark: the editor (`studio.css`) and `/play` (`play/play.html`), entered with a fade (`public/enter.js`). In the game everything reads like a game: no web header, a pause menu (Esc twice), game chat, cards in the world. Copy is plain and true: no claims we can't show.
- No runtime dependencies (Node 24, `node:sqlite`, TypeScript by type stripping: erasable syntax only, `.ts` imports).
- Customer ids are `${PROJECT_PREFIX}<16 hex>` (`config.ts`; `usr_` on live): match them with `USER_ID`, never a literal `usr_`.

```bash
npm start            # http://127.0.0.1:8800 ; needs HAWKESGEN_URL and HAWKESGEN_KEY (a key with projects ["usr_*"])
npm run typecheck

```

## Testing the game locally

Some test browsers (the Claude app's own) refuse scripts from a sandboxed page on a local address. `PORTAL_DEV_OPEN_PLAY=1`
in a local `.env` serves games unsandboxed, only to localhost / 127.0.0.1 requests (`server.ts devOpenPlay`). Never set it
on the box. `?touch=1` / `?touch=0` on a play page forces the phone controls on or off.

## Deploys

Push to `main` (going live: Studio fast-forwards main to the playtested beta commit when J types
`DEPLOY hawkesgenwebsite`). No tests gate a deploy (J, 2026-10-26): agents run `npm run typecheck` and `npm test` while
developing, and beta's playtests and J's go-live are the gate. The box checks every 2 minutes (`hawkesgen-portal-pull.timer`,
`deploy/pull.mjs`) and deploys a new main: fast-forward, restart, health check, rollback if unhealthy (that commit is then
skipped). `HAWKESGEN_PULL_TESTS=1` in the pull unit's environment brings back typecheck and tests on a clean copy first.
`npm test` is `test/run.mjs`: it passes at once in the box's deploy copy (`/srv/hawkes/.portal-test`, where an older pull.mjs still
runs it before deploying), so a box on an old pull.mjs takes the new one with the next main; elsewhere it runs every suite. Logs:
`journalctl -u hawkesgen-portal -u hawkesgen-portal-pull`. Push to main only with J's OK.

**Backups** (`src/backup.ts`, `deploy/hawkesgen-portal-backup.{service,timer}`, `deploy/backup-aws.mjs`; test `test/backup.test.ts`). `.data/portal.db` holds accounts, credits, the ledger and Stripe records.
- `sudo -u hawkes node src/cli.ts backup` makes a consistent copy while the server runs (`VACUUM INTO` on its own connection) at `.data/backups/portal-<UTC time>.db.gz`, then prunes to the newest 48 copies plus the newest of each of the last 30 UTC days. The timer runs it hourly (same hardening as the portal unit; `deploy/setup.mjs` installs and enables it). Check: `systemctl list-timers hawkesgen-portal-backup.timer`, `journalctl -u hawkesgen-portal-backup`.
- **Restore:** `sudo systemctl stop hawkesgen-portal`, `sudo -u hawkes node src/cli.ts restore .data/backups/<file>.db.gz` (refuses while something listens on the portal's port; checks the file is a SQLite database that passes its integrity check; keeps the current file as `portal.db.before-restore`), then `sudo systemctl start hawkesgen-portal`.
- **Off the box (J runs it; it creates AWS resources, a few dollars a month):** `node deploy/backup-aws.mjs` prints the plan and changes nothing; `--apply` (needs the `aws` CLI with credentials on J's PC) makes a private, versioned, encrypted S3 bucket (`hawkes-portal-backups-<account>`, objects expire after 90 days), an instance role allowed only `s3:PutObject` on `portal/*` of that bucket (added to the box's existing role if it has one), and a Data Lifecycle Manager policy: daily EBS snapshots at 03:00 UTC of the volumes tagged `hawkes-backup=portal`, kept 14 days. Then put `PORTAL_BACKUP_BUCKET=<bucket>` (and `PORTAL_BACKUP_REGION`, default us-east-1) in the box's `.env` (`setup.mjs --env`): the backup job uploads the day's first copy to `portal/portal-<day>.db.gz`, signed with SigV4 from `node:crypto` using the instance role's credentials (IMDSv2); no SDK. A failed upload exits 2 and the next hour tries again; the local copy stands. To restore from S3, download the object and use `restore` above.

The box: EC2 `hawkes-gen-public` (us-east-1, t3.large, Elastic IP 54.163.56.66, SSH key and state in
`hawkesstudio/deploy/.keys/gen_public_ed25519` / `gen-public.json`). Its IAM role (`/hawkes/hawkesgen-portal`) can only send
email as support@hawkesgen.ai (`src/mail.ts`, on when `PORTAL_MAIL=ses`): the welcome email on signup. Mail to support@ is
received by SES, kept in `s3://hawkes-mail-028793236279/inbound/` and forwarded to J by the Lambda `hawkes-support-forward`.

## Engine integrations (Unity next)

An engine plugin talks to the same API as everything else; nothing engine-specific is needed on the server.
- **Auth:** the user pastes a personal key from /app (`Authorization: Bearer hg_...`). (Later: sign in from the editor
  with the same OAuth as MCP clients: `/.well-known/oauth-authorization-server`, PKCE with a loopback redirect.)
- **Files in:** `POST /v1/uploads {filename}` gives a one-time URL; `PUT` the bytes to it; use the returned
  `asset:a_...` as an input. Or `POST /v1/assets` with the bytes directly.
- **Work:** `POST /v1/billing/quote` (show the price), `POST /v1/jobs` (one tool) or the MCP tools for chains;
  `GET /v1/jobs/:id` (with `queue.ahead` while waiting) or `GET /v1/events` (SSE, the customer's jobs only).
- **Files out:** `GET /v1/assets/:id/file`; outputs carry `mime` and `title` (a sprite sheet's `.json` is TexturePacker hash).
- **Credits:** `GET /v1/users/me` (balance); 402 means out of credits: open `https://hawkesgen.ai/credits`.
- **Built:** `jgriffith3433/hawkesgen-unity` (C:\Projects\hawkesgen-unity), Window > Hawkes Gen, signs in with the same OAuth
  (loopback, any port) and calls the MCP tools. `public/downloads/HawkesGen.unitypackage` is its export (re-export with
  its `HawkesGenExport` dev method when the package changes); the Asset Store listing is pending review.
